# Write new pearls under T<hex>-<slug>.md and rename on slug change

## Description

Wire the sanitiser and the resolver together on the write path, so newly
created pearls land under the new name and edits keep the name honest.

## Scope

- `cmdCreate` (`src/cli.ts`): compute `slug` from `--slug` or the title,
  store it in the front matter, and write to `todoFileName(id, slug)`.
- `import-beads`: same treatment, slug from the imported issue title, so a
  bulk import produces readable filenames rather than 400 hex names.
- The Pi extension's own create paths (tool `create` action and the TUI
  memory creation around lines 1907 / 2243 / 2274) must agree, or Pi and the
  CLI produce different layouts in the same directory.
- `cmdUpdate`: if the slug changes, rename the file inside the existing
  `withTodoLock` block — write the new file and unlink the old, or
  `fs.rename` then write, so an interrupted update never leaves two files
  claiming one id.

## The rename-on-update question

`--slug` explicitly given always renames. Whether `--title` alone should
also rename is **question 4 for Hugh**:

- rename: filenames stay meaningful, but a title fix churns git history and
  invalidates any path someone had copied;
- freeze: names can drift from titles, but history stays clean.

Proposal: rename only on explicit `--slug`, plus a `pearls reslug <id>` (or
a flag on the migration command) for deliberate re-derivation from the
title. That keeps the common `update --title` cheap and makes renames an
explicit act. Implement the freeze behaviour unless Hugh says otherwise.

## Done when

`pearls create "Fix the login page"` produces
`.pi/todos/T<hex>-fix-the-login-page.md`, `pearls path <id>` prints it, and
`get` / `append` / `close` all round-trip against it.
